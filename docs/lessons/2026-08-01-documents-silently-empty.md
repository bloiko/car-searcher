# `SearchResponse.documents()` silently returned empty despite a genuine hit

**What happened:** Running the app against a real OpenSearch cluster for the first time (previously: zero Docker, so zero live-cluster testing since the project began), every search returned `{"results":[]}` — including queries that obviously should have matched (`"Toyota"` against a document with `make: "Toyota"`).

**Diagnosis, evidence not guesswork:** curl'd OpenSearch directly with the exact same query the app builds — 1 hit, correct. Enabled wire-level HTTP debug logging (`--logging.level.org.apache.hc=DEBUG`) on the Spring Boot process and captured the raw bytes: OpenSearch's HTTP response genuinely contained the hit with a full `_source`. Added one debug line printing `response.hits().hits().size()` vs `response.hits().hits().get(0).source() == null` vs `response.documents().size()`: `hits=1`, `sourceNull=false`, `documentsSize=0`. `response.documents()` — the `opensearch-java` 2.14.0 client's own convenience method — was the point data was lost, not our query, not OpenSearch, not deserialization in general (manually mapping `hits().hits()` via `Hit::source()` works correctly).

**Why 15/15 passing tests never caught it:** every `CarSearchServiceTest` mocked `response.documents()` directly — stubbing the exact method that was broken, at the exact layer where the real bug lived. A test asserting "given `documents()` returns X, the code returns X" is circular once `documents()` itself doesn't do what its name promises against a real client. No test exercised the real `opensearch-java` response-parsing path at all.

**Fix:** `CarSearchService.search()` now maps `response.hits().hits()` via `Hit::source()` by hand instead of calling `.documents()`. Tests rewritten to mock at that level (`HitsMetadata`/`Hit`, not `documents()` directly) — verified this would have actually caught the original bug (strict-stubs Mockito raises `UnnecessaryStubbingException` if `.documents()` is stubbed but never called; the mapping assertion would see an empty list).

**Why this matters beyond this one fix:** this is the concrete cost of "no Docker, so no live-cluster tests" — a real, working-library-method-shaped bug sat behind 100% green tests and would have shipped to production searching nothing, silently, forever. Mocking the client is still the right call given the no-Docker constraint, but it has a real, demonstrated blind spot for anything that depends on the *actual behavior* of a third-party client library rather than on our own code's logic. Worth revisiting whether a lightweight, non-Docker way to test against a real (even if minimal/embedded) OpenSearch becomes worth the investment once this class of bug recurs.
